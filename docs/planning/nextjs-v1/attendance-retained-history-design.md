## Existing actionable path and defect

An authenticated worker reads `GET /api/v1/attendance/me/exceptions` or `GET /api/v1/attendance/me/week52`. The real REST handlers delegate to `PgAttendanceStore::list_own_exceptions` / `read_own_week52`. Their shared private `linked_employee_id` selects the current Account-to-employee link under the armed Company RLS transaction, but also requires `employees.employment_status=ACTIVE`. Changing that employee to EXITED makes retained exceptions disappear and the same recorded week become not_available. Employment exit is not Account revocation or removal of otherwise authorized own retained records.

The separate `GET /api/v1/hr/attendance-records/me` already resolves the link without using employment activity. Reuse the same responsibility distinction in the existing attendance read owner. The private selector has exactly two callers, both reads. Manager reads, exception actions, substitutes, closes, leave, manual punches and week acknowledgment have separate paths.

## Required behavior and mechanical implementation guide

The read owner resolves the current linked employee in the same Company, with an active Account. It reads only that employee's surviving retained records. ACTIVE, EXITED or UNKNOWN employment status does not decide permission to read those own records. Unknown employment remains unknown; historical read access does not prove work eligibility, a legal employment relationship, payroll liability or statutory compliance.

Remove only the employment-activity predicate from the private read selector, preserving the Account-active predicate, Account-to-employee join including Company equality, current-link lookup, RLS, exact employee filters, strict query validation, bounded exception pagination/counts and existing wire shape. Document why the predicate is absent. Add no new owner, role, endpoint, schema, dependency, fallback, cache or status mode. The existing Week52 calculation/tone is unchanged and is not newly certified as a universal legal rule.

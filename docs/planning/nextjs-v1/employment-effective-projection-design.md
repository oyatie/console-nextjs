# Proposed B01 effective-time Employment projection

Status: **PROPOSED FOR REVIEW, NOT APPROVED OR IMPLEMENTED**. This design responds to the seven real-PostgreSQL failures in `.artifacts/acceptance/b01-future-effective-red-fccad07/probe.log` at fork base `fccad07`. It defines a bounded future-effective read experiment and the separate blockers for complete B01; it is not B01 acceptance or permission to activate serving. The separate two-site durability hold still applies.

## Observed ownership and failure

- The canonical Employment writer is `backend-fork/backend/crates/ontology/canonical-adapter-postgres/src/employment.rs`. `write_in_tx` appends immutable revisions and receipts (lines 609–749, 818–850), but immediately copies a future Promote/Transfer/EXITED revision into `employees` and closes `employment_heads.valid_to` (lines 765–814). `get/list` select the latest revision and require `valid_to IS NULL` without testing the current instant (lines 492–522, 535–566). A future appointment's bound directory row also inherits `employees.employment_status='ACTIVE'` from migration 0066 before appointment takes effect.
- The independent red probe `05f433f` proves future appointments appear in current `get/list`, future transfers replace current canonical and legacy state, and future exits disappear from current canonical reads while legacy eligibility becomes `EXITED`. Its as-of controls show the revisions were saved correctly. The later `1f4e371` adds an as-of read; it does not fix current reads or legacy consumers.
- Existing schema permits `ACTIVE`, `EXITED`, `UNKNOWN` (`0066_hr_core_employee_fields.sql:15–16`). The append-only legacy `employee_lifecycle_events` stores only a nonblank **text** effective date (`0071_create_employee_lifecycle_events.sql:9–30`); it cannot safely be treated as a typed current-state source without validation/backfill.

## Proposed single owner read model

Add one **read-only, invoker-rights, RLS-scoped** Employment-owner projection with `(org_id, employee_id, as_of)` semantics over revisions visible to the current transaction. Its current wrapper captures one database instant for a transaction/request; it never calls an update or waits for a timer. For a source-bound employee it selects the latest *effective* canonical revision at or before `as_of`, within the head's opening bound, and derives the status, Company, unit, position and exit from that revision. If the binding exists but the first revision is future, it returns explicit `NOT_YET_EFFECTIVE`/`is_active=false`, not the directory row's default `ACTIVE`. An `EXITED` or `UNKNOWN` revision cannot confer active-work eligibility. Cardinality conflict or an unreadable revision fails closed rather than falling back to `employees`.

The owner projection returns **state, including `EXITED`**, and an `is_active` decision. Canonical current `get/list` filter on `is_active`; a separate authorized history/detail read still returns the exited Employment and its prior intervals for former workers and audit. `get_as_of` currently returns no active head inside an exited interval, so it cannot double as that history/detail endpoint. Authorized current People/attendance/leave/org-change reads use this one projection or its exact parameterized SQL; date-specific attendance/leave checks pass the relevant business instant or interval segments described below. Use PostgreSQL indexes on `(org_id, employment_id, valid_from)` already present in migration 0214, and bound list sizes. The underlying tables retain their RLS; do not introduce a definer bypass or cross-Company cache. Within one transaction, a snapshot plus one `as_of` makes its own queries coherent; it does **not** freeze a separate preflight/approval population. The later platform confirmation barrier must cover each materialized response before emission. If that wait crosses an effective boundary, label the response with its captured `as_of` and freshness, revalidate current authority/epoch at emission, and never present it as unqualified current state; an action separately rechecks effective truth in its execution transaction.

### Exact population, approval artifact and lock order

For every `ReassignOrgUnit` operation, materialize a complete, sorted manifest of `(operation index, Company, source/destination OrgUnit, declared effective instant, employee ID, Employment ID, source-binding composite key/provenance, effective revision ID/version/digest)` plus the explicit empty-set result. Persist the manifest and a versioned canonical digest with the **request revision** at submit, not merely `headcount`; show it to reviewers and bind it into each approval decision's exact artifact digest. A draft edit invalidates this artifact and its decisions. Multiple reassignments in one proposal have **ordered per-operation** populations: simulate each prior operation's resulting state before computing the next, and at execution compare the same ordered manifest after each prior operation in the single transaction. If a proposal cannot establish those sequential populations or complete source coverage, it is blocked; a count or unordered union cannot stand in for the reviewed people. Preserve historical approval bytes and codec versions.

At execution, the shared `console_platform_db` transaction-scoped per-Company Employment population advisory lock must be acquired immediately after tenant GUC arming and **before any request-row, period, head, employee or binding row lock** on paths that may change or review this population. In particular, `preflight`, `submit`, `effectuate` and `archive` must take it before their current `lock_request(... FOR UPDATE)` call; a draft/approval path that recomputes population must follow the same order. The Employment owner and every legacy lifecycle/import/appointment/binding writer must acquire the same lock at its transaction entry, before narrower locks. The existing `EmploymentTransferPort` remains the owner seam; no adapter-to-adapter dependency is added. Under a fresh READ COMMITTED statement, execution reselects the exact per-op set and revisions at the declared instant, compares the stored digest and current authority/period state, and holds the lock through commit. A concurrent writer that commits first forces conflict, replan and reapproval; one that starts later waits. If a legacy caller cannot safely acquire the lock before an already-held row lock, use a nonwaiting attempt and fail/roll back on contention until that path is repaired; do not wait into a cycle or let it write outside the protocol. Audit every participating transaction's lock order before activation. This coarse lock can be partitioned only after equivalent predicate proof.

For **unbound legacy** rows, distinguish historical import evidence from newly created directory-only rows. Directory creation is not appointment. During the compatibility window, an explicitly classified, reconciled legacy baseline may be shown with provenance; it must not silently become canonical authority. Existing lifecycle events require an additive typed effective date, deterministic ordering and anomaly quarantine before serving them through the same projection. Convert both direct lifecycle/confirmed-exit handlers to the Employment owner's command path for bound rows. Keep the legacy event and canonical revision in one transaction with one operation identity; an unbound row needs its own explicit legacy-baseline transition until migrated. Do not make a second competing employment writer.

`employees` remains the identity/compatibility table and may be updated only with the revision **effective at the captured current instant**, never a future revision. Its physical Company/unit/status/exit columns are intentionally **non-authoritative** and can be stale after a date boundary. A bounded reconciler may repair them and report drift, but cannot gate correctness. At and after the exact boundary, every projection-aware request computes the new state from committed revisions without a worker or timer. Legacy HTTP/list/export/SSR routes that cannot be adapted to read the projection must be fenced for affected Companies before future commands are admitted; a client may receive truthful unavailable/pending status, never a stale `ACTIVE` or `EXITED` claim. Direct SQL access to raw `employees` state cannot be offered as a v1 authority surface. Until all authority-bearing raw-table readers are cut over or fenced, future commands for that Company are unsafe. Merely changing canonical `get/list`, or merely skipping the eager update, fails the red probe or leaves a delayed stale head.

## Correction and time rules requiring review

The initial bounded slice can answer **effective as-of using revisions visible now**. It must not advertise historical knowledge-time replay: `created_at` is assigned before commit, and there is no confirmed commit/knowledge marker. Add the durable knowledge marker and `known_version` selection only with the operation/confirmation design. Preserve the canonical digest/codec and old revision bytes.

The current `UNIQUE(org_id, employment_id, valid_from)` disallows a correction at the same effective instant (`0214:134–139`). Existing tests also allow `EXITED→ACTIVE` on one employment and clear legacy `exit_date` (`employment_port_as_runtime_role.rs:778–847`), yet `employment_heads.valid_to` remains at the old exit and canonical as-of would keep that reactivation invisible. Resolve these together before calling B01 complete: append a superseding revision with a new version/knowledge identity, choose the latest known version for a repeated effective instant, and derive active intervals from the winning revision sequence. `valid_to` can remain a recomputed compatibility summary of the latest effective terminal revision, never the sole historical eligibility rule. Earlier accepted effects are not rewritten; retroactive changes open accountable attendance/payroll/access repair work and retain the old answer under earlier knowledge. This is a material contract/schema change and needs separate exact-migration review.

An actual **appointment start-date correction** is a different gap. Migration 0214 makes `employment_heads.valid_from` immutable, and `write_in_tx` rejects a revision earlier than that opening (`employment.rs:690–704`). Same-instant supersession cannot repair a head opened too late, nor can creating an unrelated Employment silently preserve relationship identity. Add a separately reviewed, append-only relationship-opening correction linked to the stable Employment and source Person/employee relationship, with effective and knowledge versions, exact prior/new opening dates, evidence and independent review where binding terms change. If the opening moves earlier, the correction must also carry or link a reviewed typed initial-state revision for the newly covered interval; merely moving the bound leaves no effective attributes before the original first revision. The projection derives both opening and state under the selected knowledge version; it must preserve the former answer and prevent duplicate/overlapping legal relationships or orphaned source bindings. Before publication, reconcile attendance, leave, payroll, tenure, access and other effects across the added/removed interval. If the original relationship identity or source binding was wrong, use an explicit link/split/supersession operation with lineage rather than editing immutable head/binding rows in place. This remains a separate B01 migration and release blocker.

Use one declared time convention for lifecycle **date** events (start of the KST business date) and canonical timestamp instants. Convert `request.effective_date` once to its KST midnight instant and pass that `valid_from` separately from execution/recorded `now` through `apply_ops` → `apply_op` → `EmploymentTransferPort`; `ReassignOrgUnit` currently passes `now` (`orgchange/adapter-postgres/src/lib.rs:986,1222–1241`). An approved 1 October transfer executed on 3 October must still be effective 1 October, subject to the 1 October period and current-policy checks. A closed period blocks the late execution and opens accountable resolution work; it must not silently shift the transfer to 3 October. Already accepted misdated transfers need reviewed appended corrections and dependent reconciliation, never a rewrite of immutable accepted evidence. A caller's RFC3339 offset must not change a date or bypass the period lock. For every command, recheck effective interval, approval payload/authority, period lock, binding cardinality and expected revision at execution. A future exit is effective only at its boundary; an actual worker remains entitled to truthful prior work.

Attendance and payroll eligibility for an overnight `[start,end)` work interval must be evaluated by **segments**, split at every Employment effective transition and KST date boundary. Resolve each segment's actual employer/Company, status, work/break time and applicable rule, then reconcile the complete interval without fabricating or dropping minutes. Checking only the shift's `work_date`, start instant or end instant could pay the wrong employer, deny valid pre-exit work or grant post-exit work. If a segment cannot be proven, return a visible reconciliation conflict, not zero or a guessed all-day status. This segment-aware integration is a separate B01/B04/B06 acceptance blocker; the bounded canonical-read slice below cannot activate attendance/payroll eligibility paths until it is green.

## Bounded experiment versus B01 release

The first implementable slice is an isolated **read-only** owner projection with a new canonical current/as-of probe for straightforward future appointment, transfer and exit, with no reactivation, opening-date correction, ambiguous legacy baseline or overnight eligibility claim. It leaves the existing seven-effect red test unchanged and still failing: its legacy `employees` assertions cannot pass while the writer eagerly applies future changes. A green new read-only probe is not a B01 fix. Affected serving routes remain fenced and B01 stays **HOLD**. Enabling future-dated commands for a Company requires every authority-bearing consumer and writer to satisfy the population, time, correction, interval and rollback contracts above, plus the independent two-site barrier.

## Expand, handover, rollback

1. Expand with the read projection and typed legacy-event date; preserve migrations 0214–0240 byte-for-byte. Backfill only validated dates and binding provenance, report malformed/ambiguous records per Company, and compare projected current facts with legacy rows. No automatic overwrite of ambiguous history.
2. Deploy projection-aware readers and owner writes. Prove all authority-bearing raw-table reads are removed or explicitly fenced before admitting future-dated commands for that Company. Per-Company handover uses one writer/egress epoch; mixed old readers cannot safely serve affected Companies. A compatible rollback build must retain the projection and future-command semantics. An unmodified pre-change binary is not a safe rollback after the first future command; queue accepted commands truthfully while an owner changes, never discard or dual-apply them.
3. Reconcile exact source bindings, effective statuses, Company/unit, date bounds, receipts and dependent eligibility before handover and after rollback. Leave applied schema and immutable revisions intact. Destructive contraction or removal of legacy compatibility is separately authorized.

## Executable red-to-green evidence

The existing named red test runs from `backend-fork/backend` with:

```sh
SQLX_OFFLINE=true tools/lanes/pgtest.sh . cargo test --locked --offline -p console-ontology-canonical-adapter-postgres --test employment_port_as_runtime_role future_effective_employment_commands_do_not_change_current_truth_early -- --exact
```

For the read-only slice, add a **new** isolated runtime-role test of the projection's effective canonical state and boundary behavior. Do not alter the existing test or claim its legacy assertions green. Full writer/consumer integration must then turn the existing named seven-effect test green and prove future-bound appointment denial, transfer/exit at the exact boundary, and current attendance/leave eligibility. A no-worker boundary probe must commit a revision shortly in the future, wait until PostgreSQL reports the boundary passed, then assert a fresh projected read changes immediately while the raw legacy row may remain stale; restart the API and repeat. Test both transfer and exit, including historical detail and former-worker access. Prove every old HTTP/list/export/SSR authority route is projection-aware or fenced. Add a preflight/action race: review the exact revision-set digest for 10 active members, concurrently commit a backdated exit effective before the selected instant, then require execution to reject the changed nine-member set without transfers or receipts. Test two ordered `ReassignOrgUnit` operations whose second source is the first destination, including their same-instant revision semantics; changing a member between submit and apply must conflict even if counts match. Pause execution after comparison, start another revision/binding writer, prove it blocks on the common lock, and verify its later correction opens repair. Exercise `effectuate` and `archive` lock order, legacy writer contention, rollback and deadlock probes. An approved 1 October transfer executed 3 October must retain the 1 October effective instant, while a closed 1 October period blocks and opens resolution. Add same-instant correction, `EXITED→ACTIVE` rescission versus true rehire, earlier appointment date, overnight intervals, retro correction after payroll close, duplicate/ambiguous binding, RLS cross-Company, legacy lifecycle/direct-exit and mixed-version rollback probes. The relevant organization, attendance, leave, payroll and migration suites plus source-custody/rollback checks must pass. The current seven-effect result is **0 passed, 1 failed, 35 filtered**; none of this proposed work is yet green.

Open blockers: reviewed same-instant semantics for both ordered ordinary transfers and corrections under migration 0214's uniqueness constraint; relationship-opening correction and explicit rescission/reinstatement versus true-rehire contracts; immutable Company identity for lock keys and manifests rather than free-text labels; as-of `DISSOLVE` headcounts; segment-aware overnight attendance/payroll eligibility; exact per-operation approval artifact and complete lock-order audit; complete consumer inventory and compatible rollback binary; historical legacy-data classification; two-site confirmation; and full B01 positive/negative/recovery/browser acceptance. Stop on any current-authority read of unreconciled legacy state or a requirement to reinterpret already accepted records without a versioned correction.

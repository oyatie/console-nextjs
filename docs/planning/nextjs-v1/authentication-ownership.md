# Authentication storage ownership and recovery continuity

Design candidate revision 4, awaiting final review. Base: accepted fork-delta `f1b2c5f269cfe8648290e2ca033d9283d48c2365cf50322e2e97395caedd7c70`. Root is the only writer. R4 remains the full objective. This transition must close actual runtime SQL substitution and stale authentication issuance paths; a private empty schema or a second pool without callers is insufficient. Rounds 1–3 required concrete recovery authority, admission custody, enrollment purposes, discoverable-login semantics, lifecycle enforcement, migration classification, empty signup, private locked-out intake, protected assent, handoff UV, immutable userHandle and concurrent human matching. ## Owner and trust boundary

Keep standard WebAuthn and the existing Rust auth/provisioning owners. Add one `console_auth_cmd` login with distinct credentials, NOINHERIT, NOSUPERUSER, NOBYPASSRLS, no memberships, no object ownership, no schema CREATE and no TRUNCATE. Reuse existing command-pool connection identity, timeout, reset and readiness checks. There is no runtime-pool fallback. Ordinary runtime SQL cannot acquire this role or mint/modify authentication evidence. The trusted Rust auth owner holds the command credential; moving arbitrary JSON writes behind a SQL function would not replace that trust.

Use direct, explicit DML only on owned authentication tables and the limited identity/provisioning columns they already require. Do not create a second workflow engine, SQL cryptographic verifier, service per tenant or new canonical-writer exception. SQL SECURITY DEFINER operations are reserved for genuinely constrained cross-owner transitions/projections; fixed qualified names, locked search_path, no dynamic caller table/expression/role, PUBLIC execution revoked.

Authentication custody includes credentials, ceremonies, ceremony bindings, bootstrap credentials, refresh families/tokens, device-login handoffs and admission rate counters. Ordinary runtime loses credential JSON, challenge state, token hashes and all mutation privileges, including inherited column/PUBLIC/default/role/view/function/trigger paths. Retain only necessary narrow read projections for credential summaries/existence and current family validity. No raw protected proof or credential material is returned by a read projection.

Additional command privileges are limited to: `users` INSERT(id,display_name,phone,roles,team,is_active,org_id); roster UPDATE(display_name,roles,team); bounded user/branch/region reads; user_branches SELECT/INSERT/DELETE; existing named Company/Group creation/read operations; existing transactional audit append; and the constrained free-entitlement operation below. No users ID/home-Company UPDATE or user_branches UPDATE/TRUNCATE. Person-reference validation uses a narrow auth-only projection of exact Company/Person ID+revision, without HR attributes. No direct canonical Company/Person/Employment/payroll DML. Identity profile/workspace and unrelated domain writes retain their owners.

## Persistent state and immutable identity

Add a private `auth_security` schema through migration0226+, owned by the migration owner, inaccessible to ordinary runtime. Keep existing public table names/IDs and add version columns rather than rekeying. Protected account security state stores Account UUID, immutable home Company UUID, monotonically increasing authentication generation, enrollment provenance/state, revision and retirement evidence. It does not store Person demographics or assert verified humanity. Keep minimal security tombstones independently of Account/Company FK cascades and the force-removal public-table scan. A retired Account UUID cannot become an initial enrollment again.

`ever_enrolled` never returns to false. Existing credentials establish recorded enrollment, not human proof. Existing audit/consumption evidence may establish previous enrollment; ambiguous legacy zero-key accounts are unresolved/recovery-required, never silently classified as never enrolled. Migration must account for each existing open bootstrap/enrollment/session state and preserve its evidence; ambiguous work creates explicit repair/recovery state. Clean installation inserts no Accounts, Companies, verified roots or fake business records.

Credential identity consists of stable credential row/credential ID, RP context and immutable public-key identity/version. Mutable standard-library counter/backup state is separate; it cannot change ownership or key identity. Record revocation separately from live-key removal so deletion does not erase enrollment history. Account security generation binds ceremonies, bootstrap credentials, handoffs and refresh families. Unknown/missing state fails closed for issuance and consumption; never infer eligibility from `count(keys)==0`.

### Account lifecycle enforcement

Create the security row through an owner-only trigger on `public.users` INSERT, including runtime identity insertion, signup, roster imports, tenant/Group creation and their SECURITY DEFINER functions. A newly allocated UUID with no protected history starts `never_enrolled`; this is permission to request first enrollment from the auth owner, not an issued credential or verified Person. The trigger rejects any UUID already in security history, including retired records. Backfill precedes installing the trigger. INSERT/UPDATE of ordinary profile/role fields cannot modify this state. UPDATE of an existing Account UUID or home Company is rejected. There is no `ON CONFLICT` reset of protected state.

On `users.is_active=false`, an owner trigger locks its protected state, advances the authentication generation once for the actual active-to-inactive transition, marks enrolled/ambiguous accounts recovery-required and sweeps credentials, admissions, enrollment authorizations, bootstrap, handoffs and families. An inactive-to-inactive UPDATE runs the idempotent sweep without repeatedly advancing the generation. The identity owner performs that UPDATE even on its already-inactive branch, and reads the trigger's protected receipt projection to preserve audit counts. That projection returns only same-Company lifecycle outcome/counts under existing Company RLS, never proof/matching material, secrets or other-Company existence. Reactivation does not clear recovery state. This replaces the proposed free-standing runtime-callable revoke helper: runtime can only cause the monotonic effect by the real lifecycle UPDATE on a row it can update under existing RLS; neither a GUC actor nor a reason string grants protected authority. Existing lifecycle authorization remains in the identity owner and is not claimed to solve all R4 employment authority.

A BEFORE DELETE trigger on `users` locks and permanently retires security state before cascading deletion. Retirement also advances Account-linkage/grant usability versions and rejects any later authority use through that Account; historical linkage records remain evidence, not active grants. Both Company-removal routines take Account locks in stable UUID order and retire first, before their child-table sweep; they cannot delete or recreate private security rows. This closes their authentication remint bypass while the separate R4 correction to preserve former-worker Accounts/history is still open. Direct auth credential deletion also preserves revocation identity. TRUNCATE is revoked on users/auth/security tables for every serving role; no serving role owns or can disable triggers.

For the pinned webauthn-rs 0.5.5 codec, the credential update trigger permits only `cred.counter`, `cred.backup_state`, `cred.backup_eligible` and `last_used_at` changes after insert; all remaining `passkey_json`, row ID, user/Company, textual credential ID and codec/RP identity are immutable. The trigger rejects counter decrease, backup-eligible true-to-false, missing/wrong-typed mutable fields and a changed JSON shape. The Rust owner obtains credential ID/public key from `Passkey::cred_id`/`get_public_key`, not caller JSON. Migration validates the supported legacy codec shape and does not rewrite existing key bytes; unknown shapes stop that Account's admission for explicit repair. SDK upgrades require a new reviewed codec, not a weakened blanket JSON UPDATE.

The detailed security tombstone contains UUID, home Company UUID, generation, recorded-enrollment flag, retirement time/reason and receipt reference only; it contains no matching attributes, key material or former-user profile. Its purpose is preventing reuse of retired authentication identities while their references, accepted sessions/evidence or recoverable backups exist. Retention uses that security record class, with annual necessity review and the legal hold/erasure owner. A separate minimal private retired-UUID denial set survives deletion of the detailed tombstone. The live INSERT trigger checks both sets, including direct runtime INSERTs; a missing detailed row is never sufficient for first enrollment. Retirement inserts that denial entry in the same transaction. No serving role may delete it. The denial set contains only random Account UUID and retirement marker, without Company, human matching data or keys, and has a disclosed anti-resurrection security purpose. Until a reviewed replacement allocation model makes historical UUID reuse impossible for all writers, retain this minimum and report that limitation honestly; do not claim total erasure while it remains. Restore must reconcile the independently preserved denial/erasure ledger before serving. This is not a legal authorization for unrestricted profile retention.

## Complete transaction and caller transition

Run an existing atomic closure on one dedicated connection; never open an auth connection halfway through a business transaction:

- Auth registration keeps key insertion, final bound authorization/bootstrap consumption and audit together. Start and finish check actual enrollment state and generation. A zero-row bootstrap consume cannot authorize first enrollment. Adding a device requires a current existing-key assertion bound to that registration intent; self-handoff has its own purpose, not ForceReset. Earlier generic step-up success is not an enrollment authorization after recovery.
- Signup, roster import, tenant onboarding and Group-account creation keep their current identity facts, initial bootstrap credential and audit together, using the narrow existing Company/Group APIs where needed. Legacy platform/role semantics do not become verified representation. The separate required R4 self-declared free passkey signup remains an explicit product acceptance item.
- Credential deletion in both identity REST and auth REST converges on the auth owner. Serialize the last-key floor with registration/revocation and preserve actual actor/target audit. The helper cannot delete another Account's credential or transfer a key.
- Identity deactivation keeps Account transition, current session-generation change, credential/bootstrap/handoff/family revocation and audit atomic through the lifecycle trigger above. An already inactive sweep remains safe/idempotent. Reactivation does not clear recovery-required state.
- Both ordinary and forced Company-removal routines must retire authentication state before deleting permitted local rows and cannot remove tombstones, reset enrollment or resurrect credentials. This is not permission to delete former-worker Accounts/history under R4; that separate lifecycle correction remains required.

Use a documented common lock order: Account lifecycle row, protected Account security row, operation/ceremony or handoff, then credential/family/token rows in stable ID order. Usernameless authentication may read narrow credential/account locator metadata first, but must lock and reread current facts before verification/issuance. Do not hold a ceremony/key lock and then acquire an Account lock. Unknown usernameless ceremonies acquire the Account lock only after the credential locator resolves it. Creation of fresh unbound ceremonies requires no fabricated Account.

All expiry checks use the database clock after lock waits, preserving the accepted single-instant final admission rule. Serializable state is authoritative; request timestamps and transaction-start time do not extend expiry.

## Session issuance, recovery and device continuity

Use a protected single-use authentication admission, not a caller-supplied Account/generation tuple. Before any proof-consuming request, ceremony/bootstrap-entry start allocates a random operation ID and 32-byte status/redemption secret; only the hash persists, attached to the pending source ceremony/intent. The Next BFF delivers the secret in a bounded HttpOnly/Secure/SameSite cookie, with Origin/CSRF validation, before it submits proof finish. Lost start responses have no consumed proof/family and may start anew. Standard proof verification and its final ceremony consumption activate an admission with that same already-held operation/secret, in the same auth-owner transaction. It records Account/home Company, current security generation, purpose, exact source credential/bootstrap/handoff identity, source ceremony, creation/deadline and terminal family/receipt. Public Rust results carry an opaque admission token with private fields; REST cannot call family issuance by arbitrary Account ID. Remove the unrestricted serving-path `issue_family(user_id, org_id, ...)` API after its callers converge. Test-only fixture issuance stays in test artifacts. Direct API callers must establish the same start-before-finish custody; a client-selected ID alone cannot authorize redemption.

Issuance locks Account/security/admission, rechecks active state, exact generation, purpose, source identity/revocation and database-clock deadline, and consumes that admission together with family, initial token and audit. No second family may reference the admission (unique constraint). Issuance uses the admission's captured generation; reading today's generation cannot upgrade yesterday's proof. Login admissions expire within five minutes and never after their source authorization deadline. Expiry cannot be extended by caller time. Refresh families store generation and purpose; rotation and current request validation require current equality and matching Account/Company. Preserve IDs, expiry caps, reuse detection and actor/delegation bindings.

For retries, protected operation status resolves the existing family/receipt under the same redemption secret and does not repeat consumption or mint another family. Only token hashes persist: a lost initial token response is reported as committed with credential delivery unavailable, requiring a fresh real login ceremony; no fabricated token or silent retry family. Source admission proof may not be reused for that fresh login. Operation IDs are not bearer authority. This rule also covers dropped device-poll responses. Current unconfirmed commit/receipt remains pending/UNKNOWN until the separate R4 durability owner can confirm it; this implementation is not two-site acknowledgment proof.

Where consumption and family creation are one owner operation, keep them in the same transaction. In particular device poll cannot commit handoff consumption before its family/audit outcome. Device approval always requires a new genuine UV assertion bound to the exact handoff, Account, source credential, generation, target and deadline; a bearer family or latest-key count is insufficient. The session-approval alias converges on this same bound-proof owner. Poll rechecks all live state. Its preexisting start-time poll secret also authorizes terminal status after a lost response; an approval token cannot poll/redeem. Restricted bootstrap/enrollment redemption likewise receives its operation/status secret at start before consumption. Recovery invalidates old approved and pending handoffs, including rows lacking old FKs. Raw JSON or matching email never establishes device trust.

Recovery locks the Account/security state, advances its generation and atomically revokes old credentials, bound ceremonies, admissions, bootstrap codes, device approvals and all refresh families/tokens. It preserves Account and approved human-equivalence identity; it cannot invent a second human. It inserts only the exact staged replacement credential approved for this operation. A replacement-key authentication bound to the recovery nonce/new-login intent is still necessary to issue a session. Failed, expired or disputed recovery does not mutate existing credentials.

An unbound discoverable ceremony has no Account generation. Recovery cannot selectively invalidate it. At assertion finish, first resolve only a credential locator, then lock Account/security, then ceremony/key and reread the active credential identity. Verify with the standard SDK and consume the challenge; the resulting admission captures the current generation. A previously consumed proof/admission cannot cross recovery. A fresh assertion using a currently authorized replacement key may legitimately use an earlier unbound, unexpired challenge; no old deleted key can do so. Account-bound step-ups/registration ceremonies carry their recorded generation and fail on mismatch. A credential locator that disappears while waiting produces denial, never an old-row fallback.

### Enrollment authorization producers and consumers

All four paths use a private `enrollment_authorizations` row with exact Account/home Company, generation, purpose, source operation/credential, registration ceremony, expiry, staged credential identity and consumed receipt. Start creates a typed intent and challenge; successful standard registration stages the candidate key without putting it in the live credential table. Final owner execution rechecks and consumes the exact authorization, activates that staged key, updates recorded enrollment and appends audit atomically. A key staged for one purpose/Account/intent cannot be activated by another.

| Purpose | Actual producer and required evidence | Final consumption |
|---|---|---|
| First enrollment | Auth owner finds protected `never_enrolled`, current active Account and one unexpired first-enrollment bootstrap source. Bootstrap redemption consumes that source once and creates only a restricted enrollment admission/session, which can access and explicitly accept its actual notices. | Same Account/generation/intent and protected current subject notice assent; the source cannot become a second normal session. Key activation marks enrolled. A new challenge can replace a canceled challenge within the same still-live authorization, never extend it. |
| Add own key | Current normal family plus a real existing-key UV assertion bound to the enrollment intent. The source key must still be active at consumption. | Exact staged key and intent; preserve existing keys/families. Generic unbound step-up success is insufficient. |
| Self-handoff | Same intent-bound existing-key assertion; issue a one-time secret bound to that Account/generation/enrollment intent for the second browser. | Redeem once into a restricted enrollment session. Recheck the original source key/family at activation. No use of `ForceReset`, no ordinary session from the handoff secret, no extension by repeated redemption. |
| Privileged recovery | The attended proofing/recovery proposal and independent exact decision described below. Subject registers/stages a replacement key and proves live UV possession, bound to recovery request and new-login nonce before review. | Execution consumes the reviewed request, replaces credentials/revokes sessions atomically; subsequent replacement-key login consumes the new-login intent to produce a normal admission. |

Restricted enrollment sessions may read/accept only their own current terms/privacy notice and create/finish/discard their own enrollment. Shared principal resolution denies business/group/delegation/device-login/refresh-to-normal use. Normal business access follows an actual login with the activated key. The old OTP route stays as a compatible enrollment entry with this explicitly changed restricted outcome; no normal Account session is minted merely because it has zero keys. Scope/purpose is server state, not a caller flag.

Subject assent is a protected typed record: Account, authentication generation, normal/restricted subject-session source, notice/terms ID+version+artifact digest, explicit accept/decline action and DB instant. Only the auth owner validating the actual subject session may create it; operators cannot accept for others. Required privacy notice acknowledgment, optional consent and service terms remain distinct kinds. An audit row is a projection, not an authority source; replace the copied `privacy.required_accept` audit lookup. Existing audit-only historical records remain evidence and require actual renewed assent where the protected gate applies; never upgrade them into new signed subject intent. Enrollment can read the exact notice before acceptance, and acceptance is required only at activation. Passkey UV alone is not assent to terms.

The pre-held HttpOnly capability grants only access to this draft, exact notice assent, standard key registration/staging and result/status; it does not arm a Company or certify corporate representation. Use existing named Group/Company creation APIs without fixed Company/sentinel IDs. Rollback leaves none of those business facts. Removing an Account's last usable key is the governed recovery/deactivation path, not a count-based shortcut.

## Minimal protected proofing and recovery owner

Implement within the existing Rust auth owner and private `auth_security` schema, with typed operations/receipt storage, using the existing audit transaction pattern. This is not a separate workflow engine or generic second governance platform. The existing governance kind+target consumer cannot serve as this authority without the exact evidence below; shared general action adoption remains subsequent R4 work. Auth action descriptors register `identity.link.v1`, `identity.verifier.grant.v1`, `identity.link.correct.v1` and `identity.recover.v1` as non-weakenable high-risk, including their aliases. Their handlers consume only owner-created exact requests/decisions. No supplied `approved` field is accepted.

Locked-out/legacy-unresolved subjects use a separate public private-intake start. The auth owner issues a random request ID and32-byte secret before any attended/key-proof submission; only its hash persists and the BFF holds it in an HttpOnly/Secure cookie. A submitted Account reference is an unverified claim and the public response does not disclose whether that Account/Company exists, its profile, linkage, passkeys or status. This capability permits only the request's private appointment/checklist, receipt/status and appeal until a current scoped verifier performs attended resolution of the exact Account. After that check the owner grants staging for this request only and may provide the subject the necessary WebAuthn challenge with that immutable Account UUID as actual userHandle, without a general profile/Company lookup. Standard registration and a live UV assertion bind the exact userHandle/Account, RP, credential identity, request and new-login nonce before independent review. A changed Account resolution discards the staged candidate and requires a new registration/proof; a resident key's userHandle can never be relabeled server-side. Staff association never upgrades the intake capability to an Account session. Only approved recovery execution and a fresh replacement-key login can issue Account authority. Capability loss permits a new intake under rate limits and attended deduplication, not automatic approval or revelation of previous requests. Requests/appointment slots expose no other reporter/subject and use their own disclosed short retention class.

### Protected records and exact decisions

- A stable random global human-equivalence ID has restricted necessary matching attributes and a revision/status (`active`, `disputed`, `revoked`). It is not a global HR directory. Company-local Person IDs/revisions remain unchanged and are mapped explicitly by a versioned linkage. Each Account has at most one active verified human linkage, with method, source-result reference, effective/expiry interval and revision. A human may have multiple Accounts; these never count as different approvers.
- Scoped verifier grants name that verified human, allowed Company/subject scope and allowed proofing/recovery actions, delegator, evidence, effective/expiry interval and version. A title, Company creation or database role does not create a grant. A Company steward cannot self-grant or extend beyond the evidence-backed delegator scope. Corporate representation evidence is distinct from personal identity and required before granting Company authority.
- Proofing intake is a private low-risk draft. Typed evidence records necessary legal name/previous-name matching and a lawful necessary date-of-birth attribute only where the approved proof method requires it, evidence type/issuer/inspection date/result, attended method/appointment, live subject challenge ID, method version and retention class. There are no arbitrary ID-number/image/recording attachments or generic medical/free-text fields. Collect no RRN, full ID number, ID image, biometric template or hashes of these prohibited values. An approved source reference identifies the check/result, not a hidden copy of prohibited ID contents.
- Before linking, compare the restricted verified matching records and prior linked names/Accounts. Ambiguous matches make the request disputed. Resolving ambiguity requires a revised attended proposal plus different verified reviewer; it cannot assert a new human just to pass independence. Authorized custodians see only their purpose-scoped evidence; ordinary callers receive a non-enumerating unresolved result. A legacy directory match alone never establishes Account ownership. Serialize every matching-namespace mutation (commissioning, create/link, merge/split/correction, matching-attribute change and erasure) with fixed native `pg_advisory_xact_lock(1311850836,1)`, reserved for auth human registry admission. Acquire this before any Account lock, rerun the complete restricted duplicate/ambiguity comparison at execution, and require a new exact proposal/decision if intervening matching evidence changes the approved target. Absent-row races must not create two human IDs for the same matching identity. This lock does not affect normal authentication; low attended-proofing volume makes one registry lock sufficient. Implementation marks that concrete throughput ceiling and uses a bounded lock timeout with truthful retry. Lifecycle retirement invalidates link/grant usability through the protected Account generation, never acquiring the registry lock after its Account lock.
- Freeze a typed request version containing action/version/codec, request/draft revision, target Account/human/Company-local Person, current authentication/linkage/grant/policy versions, evidence versions, intended change, staged credential identity for recovery, nonce, new-login intent and strict expiry. Use a versioned length-prefixed typed byte encoding for these fields (fixed order, UUID16, checked unsigned integers, UTF-8 strings with byte length, tagged options); SHA-256 binds those bytes. No arbitrary JSON canonicalization and no historical rehash. Store the frozen bytes and digest with the receipt.
- The requesting scoped verifier supplies an intent-bound live UV assertion for that request digest. A different currently verified and authorized natural person supplies an independent exact decision and UV assertion for the same digest/version. Subject challenge supplies evidence without becoming a routine third approver. Neither verifier may establish their own subject identity/recovery by claiming another Account. Ordinary recovery therefore uses a verified requester and one different verified approver; both must be different from the subject when acting as subject identity verifiers. Existing verified subjects may request ordinary own-key actions through their separate low-risk path.
- Proofing execution first acquires the registry advisory lock above, then locks all involved Accounts/security rows in UUID order, then protected human/linkage/grant/request rows in stable type+UUID order. Revalidate current active/effective scopes, distinct human IDs, exact revisions/digest, subject challenge and staged-key proofs, Account state and deadline after waits. One atomic receipt consumes the request and applies linkage/grant/recovery. An audit failure rolls back both. Changed payload or authority requires a fresh version and decision. Idempotent replay returns the committed receipt only; changed payload conflicts.
- Link merge/split, dispute, verifier revocation and material correction advance relevant revisions; unexecuted approvals referencing old revisions fail. Corrections create review work for prior effects without editing their receipt. Recovery retains the approved human ID; unknown legacy continuity must first resolve by attended evidence and independent decision, never a newly invented human ID. Unprovable continuity stays disputed with an appeal path.

### Commissioning without self-minted roots

Build a separately invoked local commissioning command; do not enable a public bootstrap route or production seed. It uses the migration/operator maintenance credential only during an explicitly authorized witnessed ceremony, with serving processes/egress fenced. This maintenance credential already has authority over the database and is outside the runtime SQL threat boundary; software cannot independently establish the first humans. The command is not an automatic startup action and is not authorized to run live by this development plan.

Commissioning requires two actual different attending humans, original-photo-ID inspection under the approved minimal method, separate pre-enrolled live passkey UV challenges, explicit attestation by both participants to their identities/distinctness and exact verifier scopes, a nonce/deadline and independently retained signed ceremony manifest. The operator records lawful necessary matching check results, witness identities/method/date and exact accounts/keys/scopes, never identity photos/recordings/numbers. One participant requests and the other witnesses/approves; no routine third approver is introduced. Human honesty/noncollusion and maintenance-custody integrity are explicit trust assumptions, not a claim that signatures prove physical identity.

The command verifies both genuine WebAuthn challenges against the frozen manifest digest and checks stable active Account/key ownership. It atomically records the ceremony receipt, two root human linkages and bounded platform verifier grants only if no accepted commissioning receipt exists. It cannot overwrite existing roots or reset the ceremony marker. Repeated same operation resolves its receipt; changed replay fails. Subsequent grant changes/recovery use the ordinary independent protected owner. Insufficient independent verifier quorum, including recovery of either of only two roots where the subject cannot verify themself, needs a separately reviewed operational recovery ceremony; an empty grants query never reopens initial commissioning. The UI reports this exact authority limitation, without a title override. Isolated test fixtures exercise real signatures and constraints but are explicitly not evidence of live commissioning.

## Explicit legacy classification

No legacy record becomes a verified human or corporate authority. Preserve all source evidence and record classification reason/codec/version in the migration report. Authentication generation starts at a recorded legacy boundary and is not confused with current `subject_authz_versions.session_generation`.

| Observed state at upgrade | Classification and allowed continuation |
|---|---|
| Active Account with valid existing passkey codec | `enrolled`; preserve key/credential/RP bytes. Bind current active families to the legacy generation. Normal fresh signed login/rotation remains possible; still human-unverified. |
| Inactive Account, even with credentials/families | Inactive/recovery-required; revoke outstanding authentication material at upgrade, preserve its evidence. Reactivation never authorizes initial enrollment. |
| Zero keys but consumed bootstrap, recorded registration/revocation/reset audit, or active normal family | `recovery_required`; previous enrollment or ambiguity exists. Revoke active families and open bootstrap effects with reason. Attended continuity/recovery is required. |
| Zero keys with an open first-enrollment bootstrap but no durable complete provenance | `unresolved`; do not infer never-enrolled from absence of keys/logs. Preserve but invalidate the old bootstrap for execution. Attended resolution is required. |
| Zero keys with no authentication history | `unresolved` for every pre-existing Account, because retained history may be incomplete. No automatic first enrollment. |
| Pending registration, step-up or approved device handoff without generation/source binding | Preserve and mark superseded; fresh proof is required. Approved handoffs cannot mint a family at the new boundary. |
| Unbound unconsumed discoverable login ceremony | Preserve challenge and original strict expiry; late bind to current active immutable key when asserted. It cannot carry an old successful proof. |

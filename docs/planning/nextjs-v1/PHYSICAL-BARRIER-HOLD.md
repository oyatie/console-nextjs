# Physical PostgreSQL confirmation boundary: unarmed implementation

Base fork HEAD: `05c4f02c0344ff69d3e3e92dfb70de99871536e1`. This slice adds an observer and a dormant epoch marker, not write-ready activation or a deployed two-site guarantee.

`console-platform-db::durability::confirm_post_commit` holds direct authenticated connections to a pinned PostgreSQL 18 primary and physical standby. After the caller's COMMIT, it captures the primary WAL INSERT-LSN upper bound and requires current-primary flush plus a matching primary replication row and independent standby flush/replay at or above that bound. It rechecks system identifier, WAL timeline, role, endpoint, source connection and a replicated monotonic writer-epoch marker before returning `ConfirmedWalPrefix`. Missing, ambiguous, stale, paused or timed-out evidence fails closed. The result proves a WAL prefix on the two observed PostgreSQL processes; it does not identify which business operation committed unless the caller first reconciles that operation by stable identity.

Migration `0236_platform_durability_epoch.sql` creates only the singleton marker schema and monotonic update/delete guard. It inserts no epoch, grants no ordinary runtime access and arms no sender. A witnessed coordinator must provision a narrow observer credential, install and advance the marker under an external monotonic lease, prove independent physical sites, and positively fence the old writer and every egress path. The fork has no such lease/witness or network/process fencing authority. Supplying a matching `ExpectedWriter` value from application code or a replicated marker alone cannot replace it.

The physical test command is `backend/crates/platform/db/tests/run-durability-physical.sh` with `PG18_BIN` pointing to PostgreSQL 18 binaries. It starts and removes two disposable physical-replication processes under a private temporary directory, uses SCRAM over loopback, and exercises success, replay lag, primary/standby aliasing, stale epoch/system/timeline, restricted marker access and a canceled synchronous COMMIT wait. PostgreSQL 18.6 returned COMMIT success after `pg_cancel_backend` while standby replay remained paused; the observer denied confirmation until replay resumed and then found the same row on the standby. Final run: one discovered, one executed, one passed; log SHA-256 `84f06dc8620c1ba5c69d23edb63c1a227d122007d618de3ee3c13ff54e93bf6e`. These two test processes share one physical machine and do not prove independent site failure tolerance.

Serving readiness, ordinary writes, protocol acknowledgments, outbox claims, mail/Matrix/Office egress, safe reads and recovery clones remain outside this slice. Each must adopt the boundary only after the external witness and fencing path exists, and must preserve UNKNOWN status when COMMIT response or confirmation is uncertain. A standby count, `remote_apply` setting, or HTTP middleware alone cannot close those paths. The existing standalone-primary readiness regression remains red.

Premortem: an untrusted epoch input or unfenced old sender could make a correct WAL observation appear to authorize a stale process. Blast radius would include every acknowledged write and external effect. Detection requires site-loss, epoch-race, stale-sender and protocol fault tests in addition to the local physical test. Rollback is code deactivation with the additive marker left dormant; schema contraction and lease recovery require separate approval. Stop activation on missing external witness, endpoint/site proof, old-process fencing, or any success acknowledgment before confirmation.

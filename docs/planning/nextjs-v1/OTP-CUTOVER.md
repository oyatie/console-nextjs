# OTP source and session-purpose cutover — implementation hold

This is a bounded implementation guide, not an activated design or acceptance result. The independent backend fork was read at local HEAD `fde90f76ea97c2b195db8edeef1c46daba025b14`; migrations 0230–0234 only expand private Account, admission, intent, provenance, role and Company-RLS structures. Serving code still issues version-0 OTPs and ordinary version-0 families. The current signed HTTP suite has four source/purpose failures, and the additional replacement-family probe below is red. No production authentication code or migration was changed for this record.

## Dependency order

1. **Freeze the live shape and classify legacy state.** Inventory every OTP issuer, passkey/device-login path, family creator, refresh path and consumer of `validate_current_claims`. Review version-0 Account states (`legacy_key_pending`, `unresolved`, `recovery_required`) against retained passkey and removal evidence. Never infer `never_enrolled` from a zero passkey count, and never rewrite version-0 provenance. Decide how existing valid passkey holders reauthenticate after old families are denied. Preserve credential IDs, RP identity, current sessions/revocations and receipt lookup.
2. **Resolve recovery and enrolled-device handoff before changing issuers.** Migration 0230 permits version-1 OTP issuance only with `issuance_purpose='first_enrollment'`. Current `admin_credential_reset` issues an OTP after deleting existing keys, and `issue_self_enroll_handoff` also issues one for already-enrolled Accounts. Neither can honestly be labeled first enrollment. Same-browser add-own-key uses a current normal family plus an intent-bound existing-key UV assertion. Cross-browser self-handoff needs its own one-use typed secret yielding only restricted enrollment authority; existing `device_handoff` is a **normal login** source and cannot be reused for it. Privileged recovery needs an exact approved source/ceremony bound to prior human identity, Account generation, replacement key and new-login intent. The existing admin reset authorization alone does not meet the approved independent-human recovery rule. Keep these paths on hold rather than silently tagging them as first enrollment.
3. **Add the command and validation owner without activating it.** In a new additive migration after 0234, provide a narrow Company-scoped audit append owner, a session validator that checks family purpose/version against private `account_state.auth_generation`, and narrowly scoped signup/profile and rate-limit operations required by the auth transaction. `console_rt` cannot read private `auth_security.account_state`; granting it table access or using handler-only claims is insufficient. `console_auth_cmd` is currently NOLOGIN, membership-free, lacks audit INSERT and is reset to NOLOGIN by `ops/postgres-reconcile-topology.sh`. Arrange a distinct serving credential/pool and an explicit post-migration role activation path; retain the 0232 migration bytes and its clean-install NOLOGIN precondition. Prove the command role has no ownership, BYPASSRLS, business-table write or cross-Company authority. Move all protected auth writers to this owner before revoking `console_rt` auth writes.
4. **Make admissions and families atomic.** The one-use-at-redemption rule from `authentication-ownership.md` is an implementation design candidate pending final cutover review; it is **not** an approval of changed R4 plan bytes. Hold an operation ID and random status secret on the client *before* consuming proof; the current one-call OTP body has no such preheld recovery secret. A reviewed two-phase or client-supplied operation protocol must create the pending private admission, then lock Account/security state and exact version-1 OTP source/generation, consume that source **once**, mint an **enrollment** family/token, append bound audit and finalize one receipt in one transaction. The family `source_operation_id` is the admission/proof operation, while the private admission records the OTP issuance operation. A lost response resolves to `committed, token unavailable`: token hashes cannot reconstruct the bearer, and the same operation cannot mint a second family. A retry needing a new usable token requires a separately authorized new source. Passkey login and genuinely approved device login create **normal** families through their own exact proof path. Generation or source revocation makes unexecuted admissions unusable.
5. **Enforce purpose at every request boundary.** `auth/src/refresh.rs` must validate and preserve immutable family purpose and Account generation; refresh must not upgrade enrollment to normal when a passkey appears. Stage a database-backed `request-context/src/lib.rs` validator that will reject enrollment and unresolved/version-0 families for business, platform, group, realtime, SSR and export authority at activation. It cannot reject version 0 while passkey login still mints version 0; the normal passkey issuer and validator switch together after fencing old processes. `auth-rest/src/lib.rs` may allow enrollment only for the exact consent, first-enrollment and permitted handoff operations. The manually locked family check in `approve_device_login_session` must require a current **normal** family inside that transaction; merely seeing a live family and a latest passkey is insufficient. No JWT display hint or `requires_passkey_setup` flag grants authority.
6. **Bind registration to one accepted authorization.** Start stores an immutable `registration_intents` row for the exact Account, Company, accepted admission/family, generation, ceremony and consumed OTP row/issuance operation (or a separately verified add-device step-up). Finish locks Account/security state first, then intent and accepted admission/family/source; it rechecks current generation, purpose, consent, authorization deadline and source revocation/replacement. It does **not** require an unconsumed A source or consume A again: A was consumed in its accepted admission. Key activation, Account enrollment state, consumed intent and audit commit together. OTP B issued after consumed A must atomically revoke/fence A's enrollment family and dependent intents/admissions, or advance the Account generation; otherwise A remains live despite replacement. An A-started ceremony cannot adopt B, and a failed finish rolls back its ceremony and key. Add-device intent has no OTP consume and requires its own still-valid step-up proof. The enrollment authorization ends no later than the original source window; challenge replacement and refresh cannot extend it, and the family absolute cap still applies.
7. **Fence old serving code, then activate issuance.** Deploy dormant purpose-aware validators/refreshers and version-1 passkey/OTP issuers to all web, API, worker and realtime processes. Prove old instances are drained and positively fenced, then atomically activate version-1 normal passkey issuance, version-1 restricted OTP admission and version-0 business denial under one writer epoch, with a tested reauthentication path for valid legacy passkey holders. Do not enable version-0 denial while any issuer still mints version 0. The old binary treats any live family as ordinary and can refresh enrollment into a full JWT. It is unsafe during activation or rollback. Revoke runtime auth-write ACLs only after all callers have moved and the negative grant tests pass. Keep schema changes additive; do not drop legacy columns, credentials or historical rows in this cutover.

## Rollback and stop conditions

Rollback serves a purpose-aware compatibility build with version-1 issuers disabled while retaining the family and private-generation validator. If that build is unavailable, prohibit traffic to old auth/business validators until every family whose authority they cannot prove has been fenced/revoked, including version-1 normal families with private generation state and any version-0 OTP-derived family; require fresh proof afterward. Revoking version-1 enrollment families alone is insufficient. Do not send traffic to the pre-cutover binary with an unproven live family, restore a stale authentication snapshot, reclassify version-0 rows as first enrollment, or run a destructive down migration. Stop activation if recovery/add-device meaning is unresolved, old processes cannot be fenced, the command audit path is incomplete, private generation cannot be validated, or an accepted admission lacks the required durability/receipt barrier.

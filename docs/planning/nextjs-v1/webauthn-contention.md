# WebAuthn verification under contention

Base: accepted fork-delta `d6fa0a252185178df5f41c898ab7af534bc3ecd290ad9d57b68f004c8b1ec723`. Root is sole writer. This necessary authentication-owner correction precedes the larger authentication-role/recovery and exact proofing transition. It does not grant proofing authority or complete that transition.

## Traced boundary

`PasskeyService` owns registration, discoverable login, generic step-up and mobile-bound step-up. All four use `claim_ceremony_tx`, whose expiry predicate uses PostgreSQL transaction-start `now()`. Registration then waits on the Account row; the three assertion paths read a credential without a row lock before updating its mutable counter/backup state. Thus a lock wait can outlive a ceremony and concurrent assertions can verify against stale key state. Standard WebAuthn verification itself already exists and must be reused.

Callers include auth REST login/device approval/registration/handoff, workflow publication, identity, inbox, registry, finance, work-order mobile and room-poll mobile paths. Preserve their signatures, bindings, UV requirements, successful response shapes and token behavior. The generic login/step-up purpose overlap and absence of exact action payload binding remain separate required work, not fixed by expiry checks.

## Implementation contract

1. Extend only the existing auth owner. No new service, dependency, schema, public endpoint or credential format. Keep credential/RP IDs, stored keys, existing ceremony kinds, foreign keys and historical audit bytes.
2. Lock the matching unconsumed ceremony row in the caller transaction. Check its server-owned expiry against a database wall-clock sample after acquiring that lock. Do not use request time or transaction-start time for acceptance. Hold the row lock through the decision. A missing, consumed, wrong-kind or expired ceremony uses the existing generic invalid-ceremony error.
3. Keep registration's existing Account `FOR UPDATE` and active check. For all three assertion paths, resolve/arm the existing Company context, then read the current credential `FOR UPDATE` before deserializing/verifying/updating it. Never add an Account lock after the credential lock (deactivation already uses Account then credentials). Deleted credentials fail closed after waiting. Reuse one private assertion verifier for standard WebAuthn, expected Account/user-handle checks, optional step-up UV, and key-state update. The existing mobile wrapper retains both client/expected and persisted/expected binding checks, plus ceremony subject check.
4. After all required Account/credential locks and successful standard cryptographic verification, consume the locked ceremony with a conditional UPDATE using one materialized database `clock_timestamp()` sample shared by strict `expires_at > sampled_time`, `consumed_at = sampled_time`, and the returned timestamp; also require `consumed_at IS NULL`. Return that database consumption time for new key usage/registration timestamps and audit. This is proof-admission time, not a promise that transaction commit/network response occurs before expiry. A later audit/storage failure still rolls back everything. If expiry passed during any lock wait or verification, no credential mutation, successful audit or committed consumption remains.
5. Consumption, credential mutation and existing registration audit stay in the same transaction. Public transaction-taking registration keeps caller-owned commit/rollback. Concurrent use of one ceremony yields at most one committed success. Concurrent distinct ceremonies on one credential use its latest standard-library state, preserving the library's counter/backup rules; do not invent counter behavior or a custom cryptographic check. Pool-owning wrappers drop/roll back their transaction on cancellation. A caller borrowing a transaction through registration must propagate errors and roll back/drop that transaction on cancellation; cancelling only the borrowed method cannot release caller-owned locks. SQLx rollback cleanup is asynchronous and bounded by existing database timeouts, not guaranteed immediate.
6. Retain an early expiry check to avoid processing already-expired work, plus the final post-verification check. No blanket global serialization: lock only the ceremony and involved Account/key. Existing database transaction/statement timeouts remain unchanged.

## Test-first acceptance

Use real disposable PostgreSQL and genuine SoftPasskey signatures, with product calls made through a non-owner runtime-role pool. Owner access is confined to fixture creation, exact lock/clock observation and assertions; this scope is not proof of separate login credentials. Preserve all inherited assertions.

- Positive registration, discoverable login and both step-up variants; owner/user-handle/UV/mobile-binding errors remain rejected with unchanged key and unconsumed ceremony, and a valid retry remains possible.
- Expiry while waiting on the ceremony row for all four paths; expiry while waiting on the credential for each assertion path; expiry while registration waits on the Account. Observe actual blocked PostgreSQL sessions, let the DB clock pass the stored deadline, then release the lock. Do not count a guessed scheduling sleep as contention proof.
- Concurrent distinct assertions for the same real key, across login/generic/mobile path combinations: arrange a higher-counter assertion before a lower-counter assertion, require the latest library-verified key state and no stale overwrite. Assert consumed/unconsumed state according to actual accepted verification and library rejection; preserve actual signature data.
- Deletion of the locked credential before waiter resumes fails without consumption; expired/equal-or-past deadline rejects; failed cryptographic verification leaves a valid retry; caller transaction rollback removes registration and consumption together. Cancel a pool-owning task blocked on a key, observe eventual lock release within a bound and no committed consumption/key change; a caller-owned registration transaction must be explicitly rolled back/dropped. Bound observer/task waits so failures are visible. Accepted consumption must be strictly before stored expiry, and key usage/creation time must equal that consumption time.
- Existing `webauthn_ceremony`, `webauthn_ceremony_replay`, `webauthn_registration_deactivated_user`, runtime-RLS provisioning chain and mobile binding tests continue to pass. Discover and execute exact test counts, format, focused Clippy and frozen-source/migration integrity. Do not substitute static source assertions for behavior.

## Risk, rollback and remaining work

Pre-mortem: a helper accidentally weakens UV/mobile binding; expiry is checked before the actual wait; stale JSON overwrites newer state; extra locks invert deactivation order; failure consumes a valid challenge. Detection: real signed positive/negative/concurrent/rollback tests on every path, exact lock observation and independent candidate review. Blast radius: `platform/auth/src/webauthn.rs` and focused tests. No live rollout is authorized. Fix forward on regression; restoring expired-proof acceptance is not a safe rollback. Stop on changed key formats/identity, new bypass, deadlock, lost audit/rollback behavior or failed required tests.

Selected lenses: Red Team, Operability/Day-2, Blast radius, Zero trust, Essentialism. Full R4 still requires private auth command ownership, protected monotonic recovery state, atomic refresh-family revocation, exact action/payload/authority-bound proofing, independently verified human linkage, two-site durability and all module/release suites. No ACL or human-independence claim follows from this correction.

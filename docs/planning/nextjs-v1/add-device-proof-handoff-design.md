# Add-device proof and cross-device enrollment — design candidate

Status: **proposed, unimplemented, not release-approved**. Source base is the independent backend fork `fccad07eafa0d39189f42effaf08ac7f1e3ab06f`. This record narrows the add-device part of [authentication-ownership.md](authentication-ownership.md); it does not change approved R4 plan bytes, migration 0240, production routes, or live authority. It uses exact-proof custody, zero-trust at the phone session, and Account/Company failure containment as the review lenses.

`auth-rest/src/lib.rs:841–1076` is the serving registration reader/writer. Start calls `PasskeyService::verify_step_up_for_user`, whose separate transaction consumes a generic authentication ceremony and returns `()` (`auth/src/webauthn.rs:406–432`); `PasskeyService::start_registration` separately persists a challenge. Migration 0240's public `auth_legacy_registration_bindings` retains ceremony, family, source and broad purpose, but no proving key or proof deadline. Finish inserts the key and success audit in a transaction, then checks that binding and a live family; it never rechecks the source key. Self-revocation deletes the exact key under the Account lock without advancing the private generation (`auth/src/account.rs:39–89`), so checking generation alone would not close the first probe.

`auth-rest/src/lib.rs:1685–1765` verifies the handoff step-up, then `provisioning/src/lib.rs:654–715` issues a version-0 `ForceReset` OTP in a separate transaction, then the route inserts an `auth_device_login_handoffs` row in another transaction. `/auth/otp/redeem` issues an ordinary version-0 family (`auth-rest/src/lib.rs:1269–1375`). Its `requires_passkey_setup` hint is computed from current zero-key count (`provisioning/src/lib.rs:825`), so it is false for an established-user handoff and cannot grant authority. Phone registration sees existing keys and demands a locally available old-key assertion. Further, the enrollment URL includes a device-login approval token: `approve_device_login_session` accepts a bearer and latest key without a new bound assertion, and `poll_device_login` can issue a normal family (`auth-rest/src/lib.rs:1890–2260`). Enrollment completion must never use that login poll as a shortcut.

The private `auth_security.account_state`, `session_admissions` and `registration_intents` in migrations 0230–0234 are dormant. Current business session readers include `request-context/src/lib.rs:308–405`, which checks a live family but not its purpose/generation, and `auth/src/refresh.rs:245–550`, which rotates without preserving that purpose. Migration 0240 is only version-0 race containment: `console_rt` can still write legacy auth tables. These observations are source facts, not approval to expose version-1 sessions.

## Joined owner transition

1. **Action-bound source proof.** The existing auth owner creates a registration or enrollment-handoff step-up challenge bound to the exact Account, Company, initiating **normal** family, action, generation and short deadline. A generic login challenge cannot silently become add-device authority. Before a proof-consuming finish, the client receives an operation ID and random status secret; only the hash is stored. Refactor the WebAuthn verifier to run in the caller's transaction and return the server-verified credential row ID and database acceptance instant, never a caller-provided key ID. Under one Account/security lock, verification and ceremony consumption join either the direct registration challenge/intent or the typed handoff-secret issuance and audit. A failed later insert rolls proof consumption back. Challenge persistence and intent insertion cannot remain separate commits.
2. **Dedicated handoff authority.** Keep login handoffs for login only. Add a private, Company-scoped enrollment-handoff row with hashed one-use secret, exact source step-up ceremony/key, normal initiating family, generation, Account, deadline and status. The QR carries this enrollment secret, not a login-approval token. The ordinary `/auth/otp/redeem` route must reject it with no family or audit success; only a typed enrollment-handoff redemption route may consume it. Redemption commits a protected admission, restricted **enrollment** family, token and audit together. A lost response resolves by the preheld status secret to the committed receipt with token unavailable; it does not mint a second family. The phone needs no copy of A or B. Enrollment-family validation permits only the exact staging/status operations; it denies business, group, export, realtime and login-approval authority. Refresh preserves purpose and the original absolute deadline; enrolling C does not upgrade that family. Fresh signed C login issues a new normal family. If the phone token is lost, or the QR is redeemed/staged by the wrong device, the owner offers an A-side **cancel/revoke/reissue** action requiring a current normal family and fresh bound UV proof. It terminalizes that handoff, revokes its restricted family, rejects/destroys its staged candidate under the record schedule, and records a receipt; a new handoff requires a new proof, operation and secret. The old redemption never mints a replacement family.
3. **Stage the phone candidate; confirm on A.** A stolen QR secret could otherwise be redeemed first to register the thief's phone: A's issuance-time UV proves the issuer, not the intended destination. Direct add-device start requires the current normal family and its own accepted, still-live UV proof. Phone start requires the exact enrollment-handoff family/admission and original source proof; it does not demand a local old-key assertion. Both persist an immutable registration intent binding challenge, Company, Account, generation, source family, proving key/ceremony, optional handoff row and deadline. Direct finish may activate its verified key in the same owner transaction. Phone finish verifies standard WebAuthn registration but stores the exact candidate credential ID/public key and RP/challenge binding in **private staged custody**, returning `pending confirmation`; it does not insert a live key or issue a normal session. A sees the single staged candidate and compares a human-readable code derived from its full canonical credential fingerprint plus handoff ID with the code shown by the actual phone. The code helps the person compare devices; authorization comes from a **fresh A-side UV assertion** bound to the full candidate fingerprint, handoff ID, Account, Company, generation and deadline. The issuer's current normal family and exact original source key must still be active. That approval transaction rechecks the staged signed response, consumes intent/handoff, activates only that key and appends the success audit atomically. A second candidate, changed fingerprint, stolen secret retry, canceled/expired handoff, denied approval or missing source key cannot activate. One handoff has at most one staged candidate; retries resolve its stable operation or conflict. The deadline is no later than challenge, original proof freshness, handoff, family and authorization limits. Phone polls only for terminal status, then performs a new signed C login.
4. **Independent desktop login.** An enrollment poll may report only `pending`, `enrolled`, `expired` or `unknown`, after current-authority checks; it never issues a session. If desktop login is also wanted, start a distinct device-login operation and require a fresh standard UV assertion by C bound to that operation before its poll can issue a normal family. The existing bearer-plus-latest-key `approve_device_login_session` cannot remain a normal-session producer at activation.

For every owner transaction, resolve immutable Account/Company locators without trusting client identity, arm only the Account's Company RLS cell, then lock current Company status/authority with a reviewed Company-to-Account order, the Account row (`FOR NO KEY UPDATE`), private Account state, exact operation/ceremony/handoff/staged candidate, then source credential and family/token rows in stable order. Existing owners currently use Account-first order; the Company-status fence must be reconciled with their writers before implementation to avoid a reverse-lock cycle. Re-read locator, active status, exact family purpose/revocation, generation, source-key existence, proof/deadline, consent and authority after waits, sampling `clock_timestamp()` for final admission. Account mutex serializes revocation against activation: if A's deletion commits first, approval denies; if activation commits first, later A deletion does not retroactively erase C. A family/source/generation change, Company suspension or recovery must fail closed. No live key, consumed intent, success audit or normal token survives a denied approval; a staged candidate remains visibly pending or rejected until its separate retention clock destroys it. Cancellation competes with approval on the same locked handoff and has one terminal winner; replay of either operation returns its original receipt, never a second key/family.

## Migration, compatibility, rollback and proof

Append migrations after 0240; preserve applied bytes, UUIDs, credential IDs, RP context, historical version-0 rows and receipts. Extend private `registration_intents` with an explicit handoff source/typed purpose and immutable proof acceptance/deadline; add private handoff and staged-candidate custody, with one-candidate uniqueness and bounded expiry/cleanup. Extend version-1 admission/family CHECK shapes with a distinct enrollment-handoff source kind without relabeling existing OTP or normal-device-login rows. Keep Company RLS, non-owner/non-BYPASSRLS command role and denial of ordinary runtime writes. Migration 0230 intentionally permits only version-1 **first-enrollment** bootstrap OTPs; do not mislabel a handoff as first enrollment or reuse `ForceReset`. Old pending unbound step-ups, OTPs and handoffs remain historical evidence but require fresh proof at the new boundary. Explicit source/role/protocol backfill classification must precede serving cutover; no key-count inference or blanket rewrite.

Switch issuer, registration, refresh, request-context, SSR/realtime and device-poll consumers together behind a fenced writer epoch. Old binaries accept unrestricted version-0 families and unbound intents, so a mixed deployment or reversion to them is unsafe. **Build and test the purpose-aware rollback binary before handover.** It must continue or terminalize pending handoffs/candidates with their existing IDs and status secrets, accept already activated C keys for fresh login, preserve accepted receipts, and keep new purpose/generation checks. Disable new issuance during rollback, drain under one owner, and forward/replay accepted post-cutover changes before restoring ownership. Do not use a down migration, PITR rewind, runtime privilege regrant or replay of consumed proof. Fencing/revoking unproven families is emergency containment, not a no-pause compatible rollback. Existing legitimate passkey holders need a real fresh-login path after old-family denial.

Acceptance requires the revoked-source red test green through its currently unreached rollback assertions. The QR red test's **start 200** remains required; its later **finish 201** expectation must be independently reviewed and replaced by a stronger terminal sequence: signed phone finish returns pending with no live key, A observes and approves the **exact** candidate using a fresh bound UV assertion, terminal receipt confirms activation, and C logs in with its new key. Retain the original test/evidence; do not simply delete or skip it. Add signed HTTP tests for stolen QR redeemed/staged first (A cancels, revokes and reissues; old operation cannot acquire a key or second family), lost phone token with status/receipt lookup and authorized reissue, generic `/otp/redeem` denial for the typed secret, status-only enrollment poll never minting a normal family, A revoked before handoff redemption or before approval, stale generation/recovery, logout/family revoke and Company suspension during lock waits, expired proof/handoff, one-use/replay/concurrent redemption, wrong Account/Company, changed candidate fingerprint, denied audit/key rollback, purpose-preserving refresh and business/realtime/export denial. Exercise independent desktop login with separate authenticated devices and a fresh bound C assertion. Test compatible rollback with a pending staged candidate and an accepted C key. Run focused command-role/RLS, migration clean-install/populated-upgrade/interruption, current source-custody and full auth HTTP suites with discovered/executed/skipped counts; do not weaken the old tests to hide remaining failures.

This is local transaction design only. The separate [two-site durability hold](DURABILITY-HOLD.md) still prevents **every** confirmed challenge, handoff secret, token, staged-candidate acknowledgment, A-side candidate read/approval, active key, cancellation, receipt and status/poll response from outrunning the primary/standby confirmation barrier. Materialize reads under current authority, capture a post-read WAL INSERT bound and confirm it before emission; locally committed but unconfirmed state remains `pending`/`UNKNOWN` and cannot authorize approval or any downstream effect. A failed barrier after local commit is reconciled by stable operation identity and preheld status secret, never by blind replay. The signed probes and this design confer no live activation or release acceptance.
